# flb_ml_parser_ruby.c Documentation

## Overview

This file contains the implementation for the Ruby multiline parser in Fluent Bit. It handles multiline log processing specifically for logs generated by Ruby applications, including exception stack traces and other multiline output patterns.

## Purpose

The primary purpose of this file is to provide a specialized multiline parser for Ruby application logs. Ruby applications often produce multiline output, particularly for exception stack traces, and this parser handles the specific patterns inherent in Ruby log formats. The parser recognizes Ruby-specific log structures and properly reconstructs multiline messages that span multiple log entries.

## Notable Features

### State-Based Processing

The parser uses a two-state approach to handle Ruby exceptions:
1. Start state: Matches exception start patterns like `/^.+:\d+:in\s+.*/`
2. Continuation state: Matches indented continuation lines like `/^\s+from\s+.*:\d+:in\s+.*/`

This approach correctly handles the hierarchical nature of Ruby exception stack traces.

### Ruby Specification Compliance

The parser implements patterns that match common Ruby exception formats, making it compatible with standard Ruby application logging behavior. It specifically looks for:
- Exception type and message patterns
- File and line number references
- Indented continuation lines with "from" prefixes

### Efficient Pattern Matching

Uses optimized regex patterns for identifying multiline continuations in Ruby logs. The patterns are designed to minimize false positives while catching all relevant Ruby exception formats.

### Automatic Flush Mechanism

The parser uses the default flush timeout (`FLB_ML_FLUSH_TIMEOUT`) to ensure that incomplete multiline messages are not held indefinitely, preventing memory issues and ensuring timely delivery of log data.

## Algorithm Overview

The Ruby parser processing follows these steps:
1. Incoming log entries are parsed using regex pattern matching
2. State transitions are determined based on pattern matches
3. Exception start patterns trigger the beginning of a multiline message
4. Continuation patterns append to the current multiline buffer
5. When no matching patterns are found, buffered content is flushed
6. The complete message is flushed to output with preserved metadata
